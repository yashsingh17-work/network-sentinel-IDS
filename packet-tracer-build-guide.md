# Packet Tracer IDS traffic lab

This is a proposed build specification, not an executed or verified .pkt file. Use packet-tracer-lab.svg as the topology reference. Cisco Packet Tracer models network protocols; PC-PT and Server-PT are not actual Windows/Linux machines. Python, Nmap, Hydra, Scapy, Zeek, Suricata, Grafana and SQLite are separate real-computer components, not programs installed in these simulated endpoints.

## Inventory and IP addressing

Use one Cisco 2911 router, five 2960-24TT switches, three PC-PT endpoints and four Server-PT endpoints. All masks are 255.255.255.0. All hosts use DNS 192.168.20.53. Use static addressing, no DHCP, no Internet uplink, no NAT and no default route on R1. R1 routes all four directly connected VLANs.

| R1 | G0/0.20 | 192.168.20.1 | None | VLAN 20 gateway |
| R1 | G0/0.30 | 192.168.30.1 | None | VLAN 30 gateway |

| SW-DMZ | VLAN 30 SVI | 192.168.30.2 | 192.168.30.1 | DMZ switch |

## Endpoint services and transport ports

Configure each endpoint through Desktop → IP Configuration. Use its address, /24 mask, local .1 gateway and DNS 192.168.20.53.

| Service | Listener | Destination port | Setup |
|---|---|---|---|
| DMZ HTTP | 192.168.30.10 | TCP 80 | WEB-SRV → Services → HTTP → On |
| Internal HTTP | 192.168.20.20 | TCP 80 | APP-SRV → Services → HTTP → On |
| DNS | 192.168.20.53 | UDP 53 for this lab | DNS-SRV → Services → DNS → On |
| Router SSH | R1, test 192.168.40.1 | TCP 22 | Router SSH configuration above |
| Device syslog | 192.168.40.10 | UDP 514 | LOG-SRV → Services → SYSLOG → On |
| Ping | Any reachable host | No TCP/UDP port | ICMP echo type 8; reply type 0 |
| Closed-port probes | APP-SRV | TCP 21,23,443 | Leave FTP, Telnet and HTTPS unavailable/off |

Disable unused Server-PT services, including default FTP if enabled. Do not assume APP-SRV has SSH just because the original diagram labels it Linux. A PC-PT has no real Windows SMB/RDP service; TCP 445/3389 are only additional synthetic probe targets. Real DNS can use TCP 53 too; this exercise uses the simulated UDP exchange.

Add DNS A records: `web.ids.test` → 192.168.30.10 and `app.ids.test` → 192.168.20.20. On client-driven connections source ports are ephemeral and selected by the simulator. Inspect PDU Details to record them. For manually created PDUs use explicitly assigned source ports 40001, 40002, etc. HTTP replies reverse the connection endpoints and ports.

## Baseline validation

1. Wait for link LEDs to turn green. Check `show ip interface brief` and `show ip route` on R1. Check `show vlan brief` and `show interfaces trunk` on CORE. Four connected /24 routes must appear on R1.
2. Ping each endpoint's own gateway. Then from ATTACK-PC ping 192.168.20.10, 192.168.20.20, 192.168.30.10 and 192.168.40.10. Initial pings may time out while ARP resolves; repeat once.
3. From VICTIM-PC browse `http://web.ids.test` and `http://app.ids.test`. Observe DNS then TCP then HTTP in Simulation mode.
4. From ADMIN-PC enter `ssh -l labadmin 192.168.40.1`, then use LabOnly123. If an IOS command is absent in your selected model/version, inspect `?` and use Simulation mode for traffic observation rather than assuming support.
5. Generate a device event, such as shutting down and restoring an unused router interface, and inspect LOG-SRV's SYSLOG pane. Syslog contains device messages, not all transit traffic. Not all SSH failures or ACL drops produce syslog messages in every Packet Tracer version.
6. Save `ids-baseline.pkt` through Packet Tracer. This guide does not itself create that proprietary file.

## Controlled attack-like scenarios

Use Simulation mode, filter ARP, ICMP, DNS, TCP, HTTP, SSH and SYSLOG as needed, then Capture/Forward. Open Event List entries and Inbound/Outbound PDU Details. Clear user-created PDUs between scenarios; stop periodic PDUs after 10–20 seconds of simulated time.

| Scenario | Source → target | Procedure | Expected evidence |
|---|---|---|---|
| Normal browsing | VICTIM-PC → DNS-SRV, WEB-SRV | Browse http://web.ids.test | DNS response, TCP handshake and HTTP reply |
| Host discovery | ATTACK-PC → .20.10, .20.20, .20.53 | Ping the three addresses in sequence | One source contacting several destination IPs |
| Service probe | ATTACK-PC → .20.20 | Add one-shot complex PDUs to TCP 21,23,80,443, source ports 40001–40004 | Different destination ports; HTTP service succeeds, unavailable services fail according to model |
| ICMP traffic burst | ATTACK-PC → .20.10 | Periodic complex PDU, application Ping, interval 1 second | Repeated ICMP echo traffic; not proof of real denial of service |
| DNS query burst | ATTACK-PC → .20.53 | DNS complex PDU, source port 40005, destination 53, interval 1 second where supported | Repeated UDP/DNS traffic; an application-valid query may need a hostname / browser request |
| Failed SSH logins | ATTACK-PC → R1 .10.1 | `ssh -l labadmin 192.168.10.1`; manually enter an incorrect password three times | Modeled authentication failures / disconnect; not automated Hydra brute force |
| Normal volume increase | VICTIM-PC → WEB-SRV | Several browser requests or periodic HTTP PDUs | More traffic without proving malicious intent |

Complex PDU application fields depend on the source device and Packet Tracer version. Select a supported TCP application or Other when port fields are editable. Synthetic port probes do not implement Nmap's SYN-scan engine, and normal TCP PDUs do not prove SYN-flood behavior. If DNS/HTTP complex PDUs fail due to missing application data, use repeated native browser queries instead. ARP spoofing and real exploit execution need a separate VM lab.

Example analysis rules for an external IDS (proposed, not built into Packet Tracer): mark >3 distinct TCP destination ports to the same host in 10 seconds as a service-probe candidate; >2 hosts contacted in 10 seconds as discovery; >5 ICMP echo requests in 10 seconds as an ICMP-rate candidate; ≥3 failed authentication events in 60 seconds as a login-failure candidate. These demonstration thresholds also flag legitimate traffic; tune against the baseline. Authentication failures require authentication logs, not just TCP/22 packet counts.

## Protected comparison

Save a second copy as `ids-protected.pkt`. Add this stateless inbound ACL on the attacker-facing router subinterface. It allows attacker DNS queries and DMZ HTTP and denies other IPv4 entering from that VLAN. It also permits ping to the attack VLAN gateway. It is a segmentation demonstration, not an IDS detection engine or a full production firewall.

```text
enable
configure terminal
ip access-list extended ATTACK-IN
 permit icmp 192.168.10.0 0.0.0.255 host 192.168.10.1 echo
 permit udp 192.168.10.0 0.0.0.255 host 192.168.20.53 eq 53
 permit tcp 192.168.10.0 0.0.0.255 host 192.168.30.10 eq 80
 deny ip any any
exit
interface gigabitEthernet0/0.10
 ip access-group ATTACK-IN in
end
copy running-config startup-config
show access-lists
```

Repeat the same scenarios: HTTP to .30.10 and DNS to .20.53 should pass; pings/probes to victims, SSH to R1 and access to monitoring should be blocked at R1. Traffic between two hosts in VLAN 10 would bypass this routed ACL. An inbound ACL on .10 also filters replies entering from attacker hosts; use baseline mode for monitoring-initiated sessions into that VLAN. ARP is not IPv4 and is not blocked by this ACL. Use PDU drop details and ACL counters where modeled; do not promise an alert for every drop.

To restore baseline:

```text
configure terminal
interface gigabitEthernet0/0.10
 no ip access-group ATTACK-IN in
end
```

## Connecting the full IDS architecture conceptually

The original image's pipeline is sources → collectors → normalization → Python detection/correlation → database/FastAPI → Grafana/optional Node-RED. The Python rules, databases, dashboards and alert totals are proposed components, not evidence that they are running.

A separate isolated VM implementation can retain these same subnets and use a Linux router with four NICs (or a VLAN trunk), Kali .10.10, actual Windows .20.10, Linux .20.20, DNS .20.53 and web .30.10. Replace the simulated monitoring system with an IDS host using two NICs: a management NIC 192.168.40.10/24 and an unnumbered passive capture NIC attached to the virtual switch's mirror destination. Ordinary attachment to VLAN 40 does not expose traffic from the other VLANs. Specify mirror sources on the internal and DMZ segments, or capture at the routing point; router-only capture misses same-VLAN traffic. A separate mirror destination is not an ordinary switch uplink, and copied packets must not be injected back into routed traffic.

Example external-only listeners, chosen by you rather than mandated by the diagram: FastAPI TCP 8000, Grafana TCP 3000, optional Node-RED TCP 1880, optional PostgreSQL TCP 5432. SQLite uses a local file and has no network port. Zeek/Suricata and Scapy/Npcap consume packets; they do not require a TCP listening port merely to capture. These services are not configured in this Packet Tracer lab. Packet Tracer Simulation events are modeled PDUs; do not assume Wireshark on the host or Python Scapy can capture them as real Ethernet frames.
